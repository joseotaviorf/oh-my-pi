# Core Model History — AUD Payload Enrichment

**Jira:** [DPLT-564](https://quintoandar.atlassian.net/browse/DPLT-564)
**Status:** Implemented (PoC on `core_contract_history`)
**Author:** Data Platform squad

---

## Context

The existing `HistoryBuilder` framework produces a narrow event-log table from CDC transactional data. Each row captures a single field-level change, but the `payload` column was always `NULL`. This meant consumers had no way to answer questions like:

- Who made this change? (Hibernate Envers audit user)
- Why was this change made? (revision reason)
- Was this a soft delete or a hard delete?

AUD (Audit) tables generated by Hibernate Envers record every revision with full metadata. Enriching the `payload` column from AUD tables closes this gap.

## Discovery: DataHub + Trino Feasibility Analysis

Before implementation, schemas were inspected via DataHub and the join strategy was validated with live Trino queries on H1 2025 production data.

### DataHub — Schemas confirmed

**`datalake_ebdb_clean.contract_aud`** (83 fields, hive/Trino)
- `id_contract` BIGINT, `rev` INTEGER, `rev_type` INTEGER
- `ts_database_transaction` TIMESTAMP(3) WITH TIME ZONE — present directly, same column name as CDC
- `mod_status`, `mod_rent`, `mod_guarantee_type`, `mod_dt_started`, `mod_dt_termination`, `mod_is_relisting_enabled` — all BOOLEAN
- `op_cdc` VARCHAR — always `'c'` in AUD (Hibernate Envers INSERT-only semantics)

**`datalake_ebdb_clean.user_revision_entity`** (9 fields)
- `id` INTEGER — revision sequence number (joins `contract_aud.rev`)
- `ts_revision` BIGINT (Unix ms), `ts_database_transaction` TIMESTAMP
- `reason` VARCHAR, `id_user` BIGINT
- `id_principal` / `principal_type` — both NULL in all tested data

**`datalake_ebdb_transactional.contrato`** — Databricks/Delta only, not exposed to Trino. Has `ts_database_transaction` (TIMESTAMP), `op_cdc` (STRING), and all camelCase business columns.

**DQ Assertions:** No DataHub DQ coverage on either AUD table — quality was inferred from queries.

3. **Average CDC lag is ~1 s** — the join must use `ts_database_transaction` (not `ts_cdc_transaction`) to match CDC events; `ts_cdc_transaction` is payload-only metadata.

## AUD Table Comparison: Clean vs Transactional

We evaluated two available AUD sources before implementation.

### `datalake_ebdb_clean.contract_aud` (clean layer)

| Column | Notes |
|---|---|
| `id_contract` | Entity ID |
| `ts_database_transaction` | Second-precision join key |
| `rev` | Revision PK (from Hibernate sequence) |
| `rev_type` | 0=insert, 1=update, 2=delete |
| `mod_{column}` | Boolean flag — True when field changed (e.g. `mod_status`) |
| `ts_revision` | Timestamp from revision entity (clean or transactional) |
| `revision_reason` | Free-text reason (sparse ~7.6% fill) |
| `aud_user_id` | ID of the user who triggered the change |

### `datalake_ebdb_transactional.contrato_aud` (transactional layer)

| Column | Notes |
|---|---|
| `id` | Entity ID (no `id_` prefix) |
| `ts_database_transaction` | **Same** second-precision join key |
| `REV` | Same revision PK value, uppercase name |
| `rEVTYPE` | Same 0/1/2 semantics, camelCase name |
| `{column}_MOD` | Same Boolean semantics, suffix naming (e.g. `status_MOD`) |
| `ts_cdc_transaction` | **Extra**: millisecond-precision CDC timestamp |

`user_revision_entity` (clean: `datalake_ebdb_clean.user_revision_entity`) and its transactional CDC counterpart (`datalake_ebdb_transactional.usuariorevisionentity`) both provide revision metadata (`ts_revision`/`timestamp`, `reason`/`motivo`, `id_user`/`usuario_id`). `core_contract_history` uses the transactional table to keep the full AUD stack on the CDC layer.

### Decision: Use the Transactional Layer

We chose `datalake_ebdb_transactional.contrato_aud` because:

1. **Shorter lineage path** — same source as the main `contrato` CDC table; no clean-layer transformation dependency.
2. **Millisecond precision** — `ts_cdc_transaction` enables sub-second event ordering, which the clean layer cannot provide.
3. **Future clean-layer deprecation readiness** — building directly from transactional sources reduces coupling to the clean pipeline.
4. **Identical join semantics** — same `ts_database_transaction` values, same `REV`/`rEVTYPE` semantics; the switch is purely a renaming exercise.

## Join Strategy

For each CDC event, the enrichment joins `contrato_aud` on:

```
aud.id = cdc.id
AND aud.ts_database_transaction = cdc.ts_database_transaction
```

For **updates** (`op_cdc='u'`), a mod-flag discriminator further filters to the revision that actually touched the tracked column:

```
aud.{column}_MOD = true
```

When multiple AUD rows match (same ts, same mod flag), the tiebreaker picks `MAX(REV)`.

For **inserts** (`op_cdc='c'`), mod flags are never set by Envers (all False), so the join uses only the timestamp + `rEVTYPE=0` path.

---

## Delete Detection (Option A)

Hibernate Envers records `rEVTYPE=2` for hard deletes. However, QuintoAndar contracts use **soft deletes** (status transitions, not row removal), meaning `rEVTYPE=2` rows are extremely rare.

**Option A** (implemented): Enrich delete payload from AUD when a match exists; if no match, emit a minimal payload with `op_cdc='d'` so consumers can always detect deletions:

```json
{
  "payload_version": 1,
  "op_cdc": "d",
  "rev": null,
  "rev_type": null,
  ...
}
```

Consumers detect deletions via `JSON_EXTRACT(payload, '$.op_cdc') = 'd'`.

Snapshot reads (`op_cdc='r'`) **always** keep `payload = NULL` — they are not real mutations.

## Payload Structure

```json
{
  "payload_version": 1,
  "op_cdc": "u",
  "rev": 1001282439,
  "rev_type": 1,
  "ts_revision": "2025-03-24T23:22:17.000",
  "ts_cdc_transaction": "2025-03-24T23:22:17.109",
  "revision_reason": null,
  "aud_user_id": 3611825,
  "aud_values": {
    "status": "Finalizado"
  }
}
```

| Field | Source | Notes |
|---|---|---|
| `payload_version` | Literal `1` | Schema version for consumers |
| `op_cdc` | CDC row | `c`/`u`/`d` |
| `rev` | `contrato_aud.REV` | Hibernate revision sequence |
| `rev_type` | `contrato_aud.rEVTYPE` | 0=insert, 1=update, 2=delete |
| `ts_revision` | `usuariorevisionentity.timestamp` | When the DB transaction committed |

| `aud_user_id` | `usuariorevisionentity.usuario_id` | Hibernate user who triggered change |
| `aud_values` | `contrato_aud` + event config | `{ tracked_col_name: new_value }` |

## Framework Changes

### `HistoricalHelper.resolve_aud_config` (new) + `DEFAULT_TRANSACTIONAL_ENVERS_CONFIG` (new)

- The Hibernate Envers transactional convention (`revision_entity_table`, `revision_reason_col`, `revision_pk_col`, `revision_type_col`, `revision_entity_id_col`, `revision_user_id_col`, `revision_ts_col`, `revision_ts_is_epoch_ms`) was previously duplicated verbatim in every `aud_config` YAML block. It is now a single module-level default dict, merged onto the entity-specific `aud_config` by `resolve_aud_config`. Per-entity YAML only needs `aud_table`, `aud_id_col`, and `enabled`; any key can still be overridden.
- Both `HistoricalHelper.load_aud_revision_data` and `HistoryBuilder._enrich_payload_from_aud` call `resolve_aud_config` so the default is applied consistently in both places that read `aud_config`.

### `HistoryBuilder._enrich_payload_from_aud`

- `revision_type_col` / `revision_pk_col` are resolved via `HistoricalHelper.resolve_aud_config` (defaults `rEVTYPE` / `REV`) instead of being read directly off the raw `aud_config` dict.
- `ts_cdc_transaction` added to the optional columns list and surfaces in the payload when present in `aud_df`.
- `_aud_ts_cdc` added to the transient column drop list.

The join strategy, tiebreaker logic, and delete/snapshot special-casing were implemented in the initial `DPLT-564` PoC and were **not changed** in the clean→transactional switch.

### `HistoricalHelper.load_aud_revision_data`

- `revision_entity_table`, `revision_reason_col`, `revision_pk_col`, `revision_entity_id_col`, `revision_user_id_col`, `revision_ts_col`, and `revision_ts_is_epoch_ms` are all resolved via `resolve_aud_config`, defaulting to the transactional Envers convention (previously the first three were mandatory keys and the defaults for the rest were the clean-layer conventions — `id_user`, `ts_revision`, `False`).
- `revision_ts_is_epoch_ms: true` (now the default) applies the same bad-migration timestamp fix used by the clean pipeline before casting transactional epoch-ms `timestamp` to TIMESTAMP.

### `aud_config` block

Only `aud_table`, `aud_id_col`, and `enabled` are entity-specific. Every
other key (`revision_entity_table`, `revision_reason_col`,

## Multiple AUD Sources per Entity

Some entities need payload enrichment from **more than one** AUD table. The canonical case is `core_house_history`: house field changes are audited in `datalake_ebdb_transactional.imovel_aud`, while owner changes are audited in `datalake_ebdb_transactional.imovellistingrelation_aud` (HLR) — and the two tables are **not** shaped the same (HLR joins on `imovelId` instead of `id` and names its revision-type column `REVTYPE` instead of `rEVTYPE`). The framework therefore supports named AUD sources.

### `aud_configs` block (plural)

Each entry is a standalone `aud_config` (same keys, same `resolve_aud_config` defaulting) plus a required, unique `name`:

```yaml
aud_configs:
  - name: imovel
    aud_table: datalake_ebdb_transactional.imovel_aud
    aud_id_col: id
    enabled: true
  # hypothetical second source with a different shape:
  - name: hlr
    aud_table: datalake_ebdb_transactional.imovellistingrelation_aud
    aud_id_col: imovelId
    revision_type_col: REVTYPE
    enabled: true
```

### `aud_source` event-config key

`event_configs` entries with `aud_mod_col` route to a source via `aud_source: <name>`:

- **Exactly one source declared** → `aud_source` is optional and defaults to it. This keeps single-source YAML (like `core_house_history` today, or `core_contract_history` on the singular API) terse.
- **More than one source declared** → every entry with `aud_mod_col` must set `aud_source` explicitly; omitting it raises `ValueError`.
- Referencing a name that was never declared raises `ValueError`; referencing a declared-but-**disabled** source silently leaves those events un-enriched, so a source can be toggled off without touching every event_config.

### API

```python
aud_configs = self.get_config("aud_configs", required=False, default=None)
aud_dfs = None
if aud_configs:
    aud_dfs = HistoricalHelper.load_aud_revision_datasets(spark, aud_configs, args)

HistoryBuilder.build_history_for_columns(
    ...,
    aud_dfs=aud_dfs,        # Dict[name, DataFrame]
    aud_configs=aud_configs,  # List[Dict], each with a unique "name"
)
```

- `HistoricalHelper.load_aud_revision_datasets` loops the existing `load_aud_revision_data` once per entry, keyed by `name` (skipping `enabled: false` entries; duplicate names raise).
- `HistoryBuilder.build_history_for_columns` accepts **either** the singular `aud_df`/`aud_config` pair **or** the plural `aud_dfs`/`aud_configs` pair — passing both raises. Internally both normalize to the same `Dict[name, (DataFrame, resolved_config)]` shape, and enrichment groups events by `(aud_source, mod_col)` so each source's DataFrame is projected once with its **own** resolved config (per-source `aud_id_col`, `revision_type_col` casing, etc.).
- The singular API is completely untouched — `core_contract_history` required zero changes.

### Worked example: `core_house_history`

`imovel_aud` is wired as the (sole) named source, enriching the 15 tracked columns that have a matching `*_MOD` flag: `regiao_id`→`regiao_MOD`, `endereco`, `numero`, `bairro`, `complemento`, `cep`, `cidade`, `tipo`, `areaTotal`, `lat`, `lng`, `numeroBanheiros`, `numeroQuartos`, `numeroSuites`, `andar`. Not enrichable (payload stays NULL): `externalId` (no `_MOD` flag), `dataCriacao`/`atualizadoEm` (not audited by Envers), `id_user_registrant` (a `coalesce` of two source columns with distinct `_MOD` flags — ambiguous).

### Follow-up: owner-event (HLR) enrichment

`ev_id_owner` / `ev_uuid_owner` are built by the bespoke `_build_owner_events` timeline path in `load_core_house_history.py` — **not** by `HistoryBuilder.build_history_for_columns` — and hardcode `payload = NULL`. Enriching them from `imovellistingrelation_aud` / `usuario_aud` is deliberately **deferred**: an owner change can stem from `relatedId_MOD`, `sourceType_MOD`, or a plain `usuario_id` update with no HLR row at all, so the mod-flag semantics are ambiguous. Per this document's own precedent, that path needs its own Trino/Databricks discovery pass (the same rigor applied to `contrato_aud` above) before implementation. The multi-source framework (`aud_configs` + `aud_source`) is ready for it once the discovery is done.

## Extending to Other Core Model DAGs

To add AUD enrichment to another core model DAG:

1. **Add a minimal `aud_config` block** to the DAG's `prod_conf.yml` / `forno_conf.yml` — just `aud_table`, `aud_id_col`, and `enabled: true`. The shared transactional Envers convention (`usuariorevisionentity`, `REV`, `rEVTYPE`, `motivo`, `usuario_id`, `timestamp` epoch-ms) is filled in automatically by `HistoricalHelper.DEFAULT_TRANSACTIONAL_ENVERS_CONFIG`.
2. **Add `aud_mod_col`** to each `event_configs` entry that has a corresponding AUD mod column (entity-specific `*_MOD` column names).
3. **Wire `load_aud_revision_data()`** in the Spark job if it does not already load AUD data. If the entity needs more than one AUD table, use the plural `aud_configs` / `load_aud_revision_datasets` API instead — see "Multiple AUD Sources per Entity" above.
4. No framework changes required — `HistoryBuilder` and `HistoricalHelper` are generic.

If the target entity uses the clean AUD layer (e.g. `contract_aud`) instead of the transactional layer, override every default that differs from the transactional convention explicitly in `aud_config`: `revision_entity_table: datalake_ebdb_clean.user_revision_entity`, `revision_reason_col: reason`, `revision_user_id_col: id_user`, `revision_ts_col: ts_revision`, `revision_ts_is_epoch_ms: false`, `revision_type_col: rev_type` (and set `aud_id_col`/`revision_pk_col` per the clean-layer column names, e.g. `id_contract`/`rev`).
